## 三、实现过程中发现并修掉的问题

这些问题不在方案里，是实现时踩出来的，记录在此便于复核。

### 规则引擎

1. **`eval7` 只支持 7 张牌**：原实现遍历 `COMBOS_7_5`，传入 5 张（翻牌面复盘要用）时 `cards[idx]` 为 `undefined`，抛 `Cannot read properties of undefined (reading 'r')`。改成通用嵌套循环，支持 5/6/7 张，不足 5 张直接抛错。
2. **`act()` 快照顺序反了**：必须先把 `p.facedRaiseAmount = 0; p.acted = true;` 落账，再做完整加注判定与 `actedBeforeLastFullRaise` 快照。顺序反了会导致测试 19 里 Q 的重开判定永远失败。
3. **单挑翻前行动顺序**：方案 v1 曾写成「BB 先动」，v2 起修正为「BTN/SB 先动、翻后 BB 先动」。实现按 v9 正文。
4. **`createGame` 模式字符串不匹配**：引擎判断 `opts.mode === '6max'`，UI 传的是 `'six'`，导致选 6 人桌仍只建 2 个玩家。统一成 `'hu' | 'six' | 'nine'`。
5. **`refunds` 与 `direct` 重复定义**：方案早期两种说法并存，v9 定案为「`direct` 唯一结算路径，`refunds` 新局恒为空」。实现按此，并在测试 20 断言 `refunds.length === 0`。

### 界面

6. **所需胜率算错**：侧栏误用 `toCall / game.pot`，应为 `toCall / (potBeforeCall + toCall)`。底部提示先算对了、侧栏没跟上，两处数字打架。
7. **结算后胜率显示 100%**：`game.pot` 在结算时被清零，`toCall / (0 + toCall)` 恒等于 1。改成手牌结束后直接显示 `—`。
8. **`loadHands` 未定义**：调试代码调用了一个不存在的函数，`ReferenceError` 被 `try/catch` 吞掉，表现为牌谱弹窗打不开。项目里统一用 `LS.get('poker.hands.v2', [])` / `loadHands()`。
9. **6 人桌座位挤压**：原布局用 flex 竖排，6 个座位挤在一条线上。改成绝对定位 + 椭圆分布（`x = 50 + 42·sinθ`、`y = 50 + 28·cosθ`），单挑/6 人/9 人共用一套公式。

### 教学

10. **复盘翻前弃牌一刀切判「有问题」**：原逻辑「`toCall <= bb` 且牌力 ≥ 0.18 就判 mistake」，把 BTN Q5s 这种边缘弃牌也骂成错。改成三段：< 0.18 判「不错」（弃得对）、≥ 0.45 判「可接受、建议跟」、中间判「可接受、可跟可弃」。
11. **AI 翻前太紧**：6 人桌经常五个人全弃、只剩大盲收盲。加了位置修正（按钮位 +0.10、枪口位 −0.10、大盲 +0.03），并把 `AI_PROFILE` 的 call 阈值从 0.42 降到 0.34（普通档）。修完后正常牌局能进到翻牌。

## 六、AI 强度验证

`_aibench.js` 让两档 AI 直接对打（不经 DOM），按钮位每手轮换：

```
node _aibench.js 800 normal hard
node _aibench.js 800 easy hard
```

| 对局 | 手数 | 净盈亏 | 拿下该手比例 |
|---|---|---|---|
| hard vs normal | 800 | hard **+11498** | 49.8% |
| easy vs hard | 800 | easy +1404 | 50.2% |
| easy vs normal | 600 | normal +972 | 30.0%（easy 每手盈利比例） |

结论：

- **hard 对 normal 是净赢**：手数接近五五开，但 hard 赢的时候赢大池、输的时候输小池——价值下注方向是对的。
- **easy 没有被 hard 打崩**：easy 的「22% 乱打」在 AI 对 AI 里不一定是劣势（随机化会削弱可预测性），但对人类新手会持续送钱。
- **三档不是碾压式差距**：真实胜率、范围表、赔率决策这些基础改进对三档同时生效，拉开差距靠的是「估算精度」和「犯错率」。

**踩过的坑**：`createGame()` 的 `buttonSeat` 恒为 0。第一版 bench 每手重建对局却没轮换按钮位，座位 0 永远在按钮位——同档自战（easy vs easy）竟然出现 ±7170 的净差。修法是在 `playOne()` 里手动 `g.buttonSeat = i % 2`。修完后同档自战净差降到 ±2117（400 手，仍在方差范围内）。

## 七、未覆盖与风险

1. **没有真人长期对局数据**：所有 AI 行为是启发式，强度未经统计校验（比如「老手档胜率是否真的高于新手档」没测）。
2. **`check.js` 用 DOM 桩**，不是真浏览器：能抓运行时异常，但抓不到样式错位和交互细节。样式靠截图人工核对（手机端用 `_shot_mobile.js` 走 CDP 模拟真实视口）。
3. **键盘快捷键**只做了 1/2/3/4 与 Esc，没有做焦点管理和完整的 tab 顺序（方案 §12 要求「键盘可操作性」，当前满足基本操作可用）。
4. **导出只带 `assetKey`**：换机器导入后自定义头像会回退到内置头像，这是方案 §8 的既定行为，不是 bug。
5. **手机端只做了竖屏精细适配**：横屏能玩但不精致（座位更小、气泡可能贴边）；桌面端布局用 `@media (max-width: 899px)` 完全隔离，未受影响。
5. **`test.js` 依赖从 HTML 里正则抽取 engine 脚本**：如果以后 engine 的 `<script id="engine">` 标记被改，测试会直接报「找不到 engine script」，不会静默通过。
6. **牌谱上限 200 手**：超过后删最旧（方案 §8 定案），导入时同样按 200 截断。
