# 验收清单

对照 `方案.md`（v9）第十一章「四条硬指标」与第十章「六批迭代计划」，逐项列出**验收什么、怎么验、证据在哪**。

验收人不需要读全部源码，按「怎么验」操作即可。

---

## 一、怎么启动

双击 `../index.html`（Edge / Chrome / Firefox 均可）。不需要服务器、不需要联网、没有构建步骤。

自动化验证需要 Node.js（实测 v24.22.0）：

```
node test.js         # 规则引擎 104 条断言
node check.js        # 单挑冒烟
node check.js six    # 6 人桌冒烟
node check.js nine   # 9 人桌冒烟
node _sixmax.js      # 6 人桌 60 手压测
```

## 二、四条硬指标逐项验收

### 指标 1：规则可验证

**要求**：方案 §5.3 的 23 条测试全部通过；每手满足筹码守恒、底池守恒、行动合法性、牌谱重放一致；补码事件不计入单手守恒。

| 验收点 | 怎么验 | 证据 |
|---|---|---|
| 23 条规则测试 | `node test.js` | 输出 `通过 104，失败 0`，其中第 1–23 节一一对应方案 §5.3 |
| 筹码守恒 | `node test.js` 第 20 节 | 断言 `Σ sidePots + Σ refunds === Σ totalBet`，且 `refunds` 恒为空 |
| 边池分层 | `node test.js` 第 2、3、4 节 | 三层全下、死钱合并、eligible=1 走 `direct` |
| 行动顺序 | `node test.js` 第 1、24 节 | 单挑翻前 BTN/SB 先动；9 人桌 UTG 先动 |
| 短全下重开 | `node test.js` 第 19 节 | 累计短全下构成完整加注后 P 重开、Q/R/S 不重开 |
| 换街清零 | `node test.js` 第 23 节 | 三字段归零、`lastFullRaiseSize` 回到大盲 |
| 烧牌 | `node test.js` 第 21 节 | `deckState` 含 `burn` 位，翻牌后长度 8 |
| 自动补码 | `node test.js` 第 22 节 | 补码后筹码回买入额；补码不计入单手守恒 |
| 牌谱重放一致 | 打开游戏打几手 → 顶栏「牌谱」→ 点任一手 → 播放 | 回放里的公共牌、各家投入、底池与当时一致 |

### 指标 2：点评可追溯

**要求**：每条复盘点评至少引用一个对应 action 的真实快照字段，并注明范围/赔率假设；不能只依据最终输赢下结论。

| 验收点 | 怎么验 | 证据 |
|---|---|---|
| 每条点评都有假设 | 打完一手看结算弹层「复盘讲评」，或牌谱详情「当时的复盘」 | 每条下面都有「底池赔率 X% · 假设：未建模（只按自己牌力估）」 |
| 点评绑定具体动作 | 牌谱详情 → 点复盘条目右侧「看这步」 | 回放自动跳到对应 `actionIndex` |
| 不凭输赢下结论 | 故意在翻前用强牌弃牌 | 判「有问题」，文案给牌力百分比与建议，与最终输赢无关 |
| 快照字段来源 | 源码 `buildReview()` | 读 `rec.potBefore`、`rec.toCallBefore`、`rec.board`、`rec.amountBefore` 等真实快照 |

### 指标 3：数据可恢复

**要求**：刷新、导出再导入后牌谱字段和重放结果一致；旧版本数据按迁移规则可读。

| 验收点 | 怎么验 | 证据 |
|---|---|---|
| 刷新不丢 | 打完几手 → F5 | 手数、筹码、牌谱都还在 |
| 导出再导入一致 | 「牌谱」→「导出」得到 JSON → 清掉本地数据 → 「导入」 | 提示「新增 N 手」，牌谱列表与重放结果一致 |
| 去重 | 同一文件导入两次 | 第二次提示「新增 0 手」 |
| 笔记一起走 | 写笔记 → 导出 → 导入 | 笔记随文件恢复，列表有 📝 |
| 迁移默认值 | 读取旧牌谱时 `loadHands()` 补 `messages: []`、`sidePots: []`、`review: null` | 源码 `loadHands()` |
| 存储键 | DevTools → Application → Local Storage | `poker.save.v2` / `poker.hands.v2` / `poker.notes.v2` / `poker.session.v2` / `poker.avatar.v1.<uuid>` |

### 指标 4：消息可追溯且不泄露牌力

**要求**：每条消息能回溯到有效 `actionIndex`；关闭消息后不再生成或显示新消息，但历史 `messages[]`、规则、AI 决策、牌谱不变。

| 验收点 | 怎么验 | 证据 |
|---|---|---|
| 消息绑定动作 | 源码 `pushMessage()` | 写入 `{ id, speakerId, actionIndex, type:'action', text, createdAt, templateKey }` |
| 消息不含牌力 | 看所有气泡文案 | 只有「这手打不了 / 跟一个 / 加点压力 / 全下了」这类模板，没有任何牌面或胜率 |
| 关消息只影响显示 | 关掉「消息」再打几手 | 规则、AI 决策、牌谱条数都不变；历史牌谱里的 `messages[]` 保留 |
| 消息模板库 | 源码 `MSG_POOL` | fold / call / check / raise / allin 五类，每类多条等价模板 |

## 四、明确不做的（§12）

以下均**未实现**，属方案明确排除：

- 在线对战、真钱、云同步
- 职业级 AI（当前是启发式，不是 CFR/GTO）
- 手机端适配（最低 1280×720 桌面优先）
- 自由聊天、联网消息、语音消息、动态表情
- P0 不做复杂范围求解（点评里的「对手范围」标注为「未建模」）

## 五、已知偏差（不算 bug，但验收时应知道）

1. **起手牌表是教学近似值**，不是 GTO 求解结果。
2. **复盘点评是规则化模板**（牌力阈值 + 底池赔率比较），不代表最优解；「对手范围」一律标注「未建模」。
3. **AI 是启发式**：牌力分 + 位置修正 + 赔率比较 + 固定概率诈唬，没有对手建模，也不会根据你之前的打法调整。
4. **牌力估计**用 Chen formula 归一化（翻前）和牌型类别映射（翻后），是粗估，不是胜率计算。
5. **头像上传**用 `canvas` 压缩到 64×64 JPEG，超过 8KB 会拒绝并提示（不静默失败）。
6. **导出只带 `assetKey` 不带图片本体**：换机器导入后，本地找不到对应图片就回退内置头像——这是方案 §8 的既定行为。
