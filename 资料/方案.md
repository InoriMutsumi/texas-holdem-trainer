## 一、一句话定位

不是做一个"能打牌的牌桌"，而是做一个**陪练工具**：你打一手，打完后给你讲评一手，并长期记录你的打法有没有变好。核心功能是"复盘"，打牌本身只是载体。

## 二、先搞清楚："学会德州扑克"到底学什么

规则十分钟就能背完，真正难的是三件事，整个游戏的设计都围绕把这三件事**显性化**来做：

| 要学的能力 | 具体表现 | 游戏里怎么教 |
|---|---|---|
| **范围思维** | 不是"我这两张牌强不强"，而是"我这个位置该用哪些牌入池" | 翻前起手牌表，按位置给可玩/边缘/弃 |
| **赔率思维** | 跟注要看底池赔率，下注要看对手弃牌率 | 实时显示"你需要多少胜率才值得跟" |
| **位置思维** | 同样的牌后位能打、前位该弃 | 座位标注位置名，起手牌表随位置变 |

**学习闭环**：打一手 → 立刻复盘 → 结论进笔记 → 下一手刻意改。这个闭环就是验收标准第 2 条的来源。

## 三、形态与技术选型

**单个 HTML 文件**（HTML + CSS + JS 全内联），双击即用：

- 零安装、断网可玩，符合"本地离线"
- 无构建、无 `node_modules`、无服务端，不会因为环境问题打不开
- 数据存 `localStorage`，纯前端
- 备份/分享就是拷一个文件
- 牌面用 Unicode 花色 + CSS 绘制，不引外部图片，保证单文件离线

不用 Canvas，用 DOM 布局——教学要读文字，DOM 排版和鼠标交互更省事。

## 四、功能分级

**P0 · 最小可玩版**（第一批交付，当天能玩）

- 单挑 1v1（第一批打通）；6 人桌紧接第二批接入（同一套规则引擎，只多座位、轮转与多人边池）
- 完整无限注规则：盲注、四轮下注、过牌/跟注/加注/弃牌/全下、**边池**、摊牌比牌、位置轮转
- 规则型 AI（会弃会跟会加，暂不诈唬）
- 底池、筹码、行动日志、结算说明（谁赢、什么牌型赢）
- `localStorage` 存筹码与牌谱
- 主控玩家和 AI 对手的头像、座位状态与基础消息气泡

**P1 · 教学与复盘**

- 翻前起手牌表（13×13 网格，按位置分色）
- 底池赔率实时提示
- 每手结束的**复盘讲评**（逐街点评关键决策）
- AI 三档难度 + 诈唬

**P2 · 长期统计**

- VPIP（入池率）、PFR（翻前加注率）、胜率、盈亏曲线
- 牌谱回放（重播任意一手）
- 自定义盲注与玩家数

## 五、规则引擎设计（出错重灾区）

### 5.1 数据结构

```
Card      = { rank: 2..14, suit: 's'|'h'|'d'|'c' }

Player    = { id, name, seat, chips, hole[2], streetBet, totalBet, folded, allIn,
              acted,                    // 本街是否已行动过（用于行动循环是否走完）
              facedRaiseAmount,         // 本街该玩家上次行动后累计面对的新增加注额
              actedBeforeLastFullRaise, // 最近一次完整加注发生前，该玩家是否已经行动过
              reopenEligible }          // 短全下累计成完整加注后，该玩家是否重新获得加注权

Action    = { street, playerId, type, amountBefore, amountAdded, streetBetAfter,
              potAfter, streetCurrentBetAfter, lastFullRaiseSizeAfter,
              raiseAccumulatorAfter, board, eligiblePlayers }

GameState = { street: preflop|flop|turn|river|showdown,
              deck[],                   // 剩余牌堆
              deckState[],              // 本手已发出的完整牌序（含烧牌位），重放的唯一依据
              board[], pot, streetCurrentBet,
              lastFullRaiseSize,        // 本街最小完整加注增量；初值 = 大盲额，每次换街重置
              raiseAccumulator,         // 本街自上次完整加注以来，未达完整额度的短加注累计
              activePlayer, lastAggressor, buttonSeat, smallBlind, bigBlind,
              sidePots[{ amount, eligible[], resolution: 'showdown'|'direct', winnerId? }],
              deadMoney[{ amount, mergedIntoLayer }],   // 可选审计：eligible=0 的死钱层、并入的目标层 index，不参与守恒断言
              refunds[{ playerId, amount }] }           // 未被跟注的超额投入退还记录（含弃牌者）
```

`acted`、`facedRaiseAmount`、`actedBeforeLastFullRaise`、`reopenEligible` 是不同用途，**不能合并**：`acted` 决定本街行动循环是否走完；`actedBeforeLastFullRaise` 区分「完整加注前已经行动、可能被重新开放」与「完整加注前尚未行动、只需正常行动」的玩家；`facedRaiseAmount` 记录玩家上次行动后累计面对的新增加注额；`reopenEligible` 是最终标记，只用于加注额度校验。原 `actedSinceFullRaise` 已删除——它的语义可由 `acted && !actedBeforeLastFullRaise` 推出，留着只会和快照时机打架。

### 5.2 关键算法

- **洗牌**：Fisher-Yates + 独立 PRNG（带种子，便于回放和复盘重算）。

- **发牌与烧牌**：每手按下述顺序从牌堆顶部取牌，并把完整序列（**含烧牌位**）记入 `deckState`：
  1. 每人 2 张底牌；
  2. 烧 1 张 → 翻牌 3 张；
  3. 烧 1 张 → 转牌 1 张；
  4. 烧 1 张 → 河牌 1 张。

  烧牌不显示、不参与比牌，但**必须占 `deckState` 的位**，否则重放一定错位。全员全下提前发完剩余公共牌时，同样按此顺序发。

- **行动合法性**
  - `lastFullRaiseSize` 初值 = 大盲额（翻前、翻后都一样；翻后它就是最小下注额），每次换街重置为大盲额。
  - 过牌要求 `streetCurrentBet === streetBet`。
  - 加注后总额须 ≥ `streetCurrentBet + lastFullRaiseSize`；`lastFullRaiseSize` 是本街最近一次**完整**加注的增量，不是某个玩家的下注额。
  - 全下可以低于最小完整加注；这种短全下不更新 `lastFullRaiseSize`，也不重新开放**已行动玩家**的加注权（但如果多次短全下累计够一个完整加注额，按下一条视为完整加注处理）。
  - **多次短全下的累计增量达到一个完整加注额时，视为完整加注，重新开放加注权**（TDA 规则）。判定分两步：每次短全下都把增量累加进 `GameState.raiseAccumulator`；当 `raiseAccumulator ≥ lastFullRaiseSize` 时，把这次视为完整加注，`lastFullRaiseSize` 更新为本次累计实际增量、`raiseAccumulator` 清零。**「更新为本次累计实际增量」是本方案自定规则**：TDA 对累计短全下后的最小加注额没有统一算法，本方案定死按累计后的实际增量算，不许改用「最后那次短全下的增量」。
  - 每个玩家只记三个玩家级字段：`facedRaiseAmount`、`actedBeforeLastFullRaise`、`reopenEligible`（另有行动循环用的 `acted`）。**生命周期写死，不许实现者临场发挥**：
    - **每街开始清空**：`facedRaiseAmount = 0`、`actedBeforeLastFullRaise = false`、`reopenEligible = false`；`lastFullRaiseSize` 同时重置为大盲额。漏掉这一步，上一街的累计值会带进下一街，造成误重开。
    - **快照时机**：本次 action **落账之后**（`acted`、`streetCurrentBet`、`raiseAccumulator` 都已更新）、**完整加注处理之前**，对每个玩家执行 `actedBeforeLastFullRaise = acted`。这里的“最后抬价者”专指触发本次完整加注的最后一个行动者（例如累计短全下中把累计值凑足的玩家）；他本人不作为本次重新开放对象。此前做过一次完整加注、随后又面对新的累计完整加注的玩家，仍可重新加注。
    - `facedRaiseAmount`：玩家每次行动后清零；此后每次 `streetCurrentBet` 上升（**无论完整加注还是短全下**），若该玩家本街**已行动过（`acted === true`）**且不是本次抬价者，则累加 `(新值 - 旧值)`。**不要**用 `actedBeforeLastFullRaise` 判断是否累加，它会过期——完整加注之后才行动的玩家会被漏掉。
    - `reopenEligible`：每次轮到玩家行动时先复位为 `false`；只有「`actedBeforeLastFullRaise === true` 且 `facedRaiseAmount >= lastFullRaiseSize` 且不是本次完整加注的最后抬价者本人」时才置 `true`。完整加注前尚未行动的玩家不走重新开放判断，只按正常最小加注行动。“最后抬价者”只指**当前这一次**触发完整加注的人，不追溯更早的加注者。
    - 完整加注发生后，只有 `actedBeforeLastFullRaise === true` 且尚未弃牌/全下的玩家被标记为可重新评估；最后抬价者本人和此前尚未行动者不因该事件获得额外加注权。禁止把加注增量与 `streetCurrentBet` 总额直接比较。
  - 短全下之后**尚未行动**的玩家不受影响，其最小加注额仍为 `streetCurrentBet + lastFullRaiseSize`；已行动玩家是否重新获得加注权由上述玩家级字段决定。这两套逻辑必须分开写。

- **大盲选项（BB option）**：翻前若所有人平跟到 BB、且无人加注（BB 的 `streetBet` 已等于 `streetCurrentBet`），BB 有权**过牌结束翻前**或**加注**。行动循环必须用 `acted` + `lastAggressor` 判定，不能因为 BB 已投盲注就直接跳过其行动权。

- **边池**
  - 按所有参与本手牌玩家的 `totalBet` 唯一层级计算增量底池：`(本层金额 - 上一层金额) × totalBet 达到本层的玩家数`。
  - 这个"玩家数"**包含已弃牌者**（他们的筹码在池里），而 `eligible` 只包含**未弃牌且 totalBet ≥ 本层**的玩家。
  - **每一层的归属分两种情况**：
    1. eligible ≥ 2 人 → 生成边池，`resolution: 'showdown'`，比牌分配；
    2. eligible 恰 1 人（**未弃牌且投到这一层的只有他**：其他人要么没投到这一层、要么已弃牌）→ 生成边池，`resolution: 'direct'`，整层直接记给该玩家，不比牌。
  - **结算前先退还「未被跟注的超额投入」**（TDA 的标准做法，v10 修正）：任何玩家（含已弃牌者）的 `totalBet` 如果超过所有未弃牌玩家的最高 `totalBet`，超出部分没有任何人能跟，**必须原路退回**，记入 `refunds[]`，`g.pot` 同步扣减。这一步在分层之前执行。
  - **eligible 为 0 人的层（这一层只有弃牌者投入）不是一种 sidePot**：完成上一步退还之后，该层在正常牌局中不会出现；若因异常数据出现，并入最近的下方可竞争层，由该层赢家分配，可记入 `deadMoney[]` 供审计，不参与守恒断言。**在无 ante、无 straddle、无其他强制投入差异的前提下，正常牌局不会产生死钱层**。理由是不变量：同一街开始时仍在牌局且未全下的玩家 `totalBet` 相等；街内跟注/过牌不制造差额，弃牌者不会比当前最高下注者投入更多，全下者不能再弃牌，无人下注时弃牌也只会保持相等。因此最后一个未弃牌者永远是最高投入者，「只有弃牌者投到」的层不存在。该分支仅作为异常数据、旧牌谱与分层函数的防御性兜底，**仍必须实现**，防止断言意外穿透。
  - **兜底层的归属是自定规则**：正常牌局不会走到这一步；若走到，并入最近的下方可竞争层、由该层赢家拿（而不是并入主池）。
  - **结算路径唯一**：先退还超额投入（记 `refunds[]`），再按 `totalBet` 分层；退还之后每一层至少有一个未弃牌玩家，`eligible` 恒 ≥ 1，`direct` 层只在「唯一未弃牌者的投入正好等于该层」时出现。**禁止同一笔钱既记 `direct` 又记 `refunds`**——退款发生在分层之前。
  - 每个比牌层（`showdown`）独立比牌、独立平分；`direct` 层直接记给唯一 eligible 玩家，不参与比牌。奇数余数从**按钮左侧第一位参与该池分配的玩家**开始，按座位顺序每人分 1 枚最小筹码单位，直到分完。
  - 硬守恒断言：`Σ sidePots.amount === 退还后 Σ 所有玩家 totalBet`（退款已从 `totalBet` 与 `pot` 中同步扣减），每次结算后校验。
  - `deadMoney` 是**纯审计记录、不参与守恒**：每个条目的 `mergedIntoLayer` 必须指向一个存在的 `sidePots` **数组下标**（不是层号），且该层 `amount` 已经包含这笔死钱。**不许**把 `deadMoney` 的金额再加回守恒等式，也不断言它等于 0。
  - `refunds` 记录退还给任何玩家（含已弃牌者）的未被跟注投入；同一笔钱只走一条路：退还走 `refunds`，分层走 `sidePots`。

- **比牌**：7 选 5 枚举 C(7,5)=21 种组合，每种评牌型取最大；评估结果用可字典序比较的数组 `[牌型类别, 主牌点数, 次级点数…]`；顺子含 A-2-3-4-5 特判。

- **盲注与位置**
  - 6 人桌座位顺序：BTN、SB、BB、UTG、MP、CO；小盲 = 1/2 大盲。
  - **盲注不写入 `actions[]`**：盲注直接作为 `streetBet` / `totalBet` 的初始值，并单独存进牌谱的 `blinds` 字段。翻前行动循环从 UTG（单挑从 BTN/SB）开始，大盲选项和「翻前是否结束」都只依赖 `streetCurrentBet` 与 `acted` 判定，不依赖盲注 action。
  - **盲注不足（短盲）**：玩家投入其全部筹码并立即 all-in，**但法定盲注额不变**。例：大盲 20、BB 只剩 5 —— BB 投 5 直接 all-in，其他玩家的 `streetCurrentBet` 仍是 20、最小完整加注额也按 20 算，**谁都不能只跟到 5**。短盲玩家这 5 个筹码只影响他自己能参与边池分配的层级（0–5 层他进，5 以上的层他没资格）。
  - 短 SB 同理：SB 法定额度是 10，他若只有 7 就投 7 all-in，其他玩家仍按完整盲注/加注额行动。
  - 唯一例外：桌上只剩一名玩家还有筹码可行动时，他不需要继续投注，直接进入发牌与摊牌流程。
  - 单挑时 BTN 兼 SB，BB 为另一位玩家。
  - **翻前单挑由 BTN/SB 先行动，BB 后行动。**
  - **翻后单挑由 BB 先行动**（BB 处不利位置），BTN/SB 后行动。
  - 多人桌翻后由按钮左侧第一位仍在牌局的玩家先行动。

- **行动顺序**
  - 6 人桌翻前：UTG → MP → CO → BTN → SB → BB。
  - 单挑翻前：BTN/SB → BB。
  - 翻后：从按钮左侧第一位仍在牌局的玩家起，顺时针到按钮结束。

- **摊牌亮牌顺序**：最终下注街的最后一次有效下注或加注者先亮；若该街无人下注，从按钮左侧第一位仍在牌局的玩家开始。只有一名未弃牌玩家时立即收池，不亮对手底牌。

- **全员全下**：仅当所有未弃牌玩家均 all-in 时，才自动按街道发完剩余公共牌；若仍有人有筹码可行动，继续正常下注。

### 5.3 验收测试用例（23 条，全部要写成自动断言）

1. **单挑翻前由 BTN/SB 先行动、BB 后行动**；翻后由 BB 先行动、BTN/SB 后行动。
2. **三层全下（均未弃牌）**：筹码 100 / 300 / 500 全下 → 主池 `100×3=300`（eligible 100/300/500）、边池 `200×2=400`（eligible 300/500）、最上层 `200×1` 只有 500 → `direct` 归 500；`sidePots = [300(showdown), 400(showdown), 200(direct)]`，`Σ=900=Σ totalBet`，`refunds` 为空。比牌结果：主池在 100/300/500 间比，边池只在 300/500 间比。
3. **三层投入（高投入者弃牌，构造数据）**：`totalBet` 直接构造为 A=100（`allIn`）、B=300（`allIn`）、C=500（`folded`）→ 层 0–100 池 300（eligible A/B，`showdown`）、层 100–300 池 400（eligible 仅 B，`direct`）、层 300–500 的 200 是弃牌者死钱 → 并入最近的下方可竞争层；`sidePots = [300(showdown), 600(direct)]`，总额 900 守恒。**本场景不对应可发生的牌局**（正常牌局不会产生死钱层，见 §5.2），只用于验证分层与死钱合并算法。合法构造的前提：`folded: true` 的玩家必须是 `totalBet` 最高者，且同一玩家的 `allIn` 与 `folded` 不得同时为 `true`。
4. **三层全下（300 弃牌）**：100、500 未弃，300 弃牌 → 层 0–100 池 300（eligible 100/500）、层 100–300 池 400（未弃牌且投到本层的只有 500，`direct` 归他）、层 300–500 池 200（同样只有 500，`direct` 归他）。断言 500 稳拿 `400+200=600`，`refunds` 为空，总额仍守恒。
5. 底池 100、当前街下注 100，有人加到 200，下一位完整加注至少到 300。
6. 短全下不足完整加注后，已经行动过的玩家不能再次加注。
7. 弃牌玩家的投入计入底池金额，但不进入任何 eligible 集合。
8. 所有人过牌到摊牌，按按钮左侧首位开始亮牌并正确结算。
9. 皇家同花顺、同花顺、四条及 A2345 顺子比较正确。
10. 公共牌本身就是最大牌型，多人平分并正确处理奇数余数（余数按按钮左侧第一位参与分配者起，每人 1 枚）。
11. 只剩一人未弃牌，立即收池且不亮对手底牌。
12. **短 SB**：盲注 10/20、SB 只剩 7 → SB 投 7 all-in，BB 仍投 20，其他玩家仍按完整额度行动；SB 只能竞争 0–7 那一层。
13. **短 BB**：盲注 10/20、BB 只剩 15 → BB 投 15 all-in，其他玩家**仍须按 20 跟注/加注**，最小完整加注也按 20 算；0–15 层含 BB，15–20 层不含 BB。
14. **按钮轮转**：一手结束后按钮移给下一位仍有筹码的玩家；有人出局则跳过，不空转。
15. **部分全下**：一人 all-in 后其余玩家仍有筹码，继续正常下注，不得提前发完公共牌。
16. **全员全下**：所有未弃牌玩家均 all-in 后，按街道发完剩余公共牌再摊牌。
17. **牌谱重放**：导出、导入、重放后的最终筹码与原结算逐位一致。
18. **大盲选项**：翻前全员平跟到 BB，BB 可选择过牌结束翻前，也可加注；选过牌后直接进翻牌。
19. **短全下累计**：当前注 100、`lastFullRaiseSize` 100。P 跟注 100 → Q 加注到 200（完整加注，+100）→ R 全下 250（+50，累计 50，非完整）→ S 全下 300（+50，累计 100，**构成完整加注**）。断言**时机均为该玩家轮到行动时**（S 之后按座位顺序先轮到 P、再轮到 Q）：`P.reopenEligible === true`（加注前已行动，`facedRaiseAmount` 累计 100+50+50 = 200 ≥ 100）、`Q.reopenEligible === true`（Q 此后又面对 R/S 的累计 100，Q 不是本次触发完整加注的最后抬价者）、`R.reopenEligible === false`（累计 50 < 100 且全下）、`S.reopenEligible === false`（本次触发完整加注的最后抬价者且全下）；S 之后的下一位最小加注额 = 300 + 100 = 400。**反例**：把 P 换成全程未行动的玩家 U，U 的 `actedBeforeLastFullRaise === false`，不进入重新开放判断，轮到他时只按正常最小加注 400 行动。
20. **边池守恒**：任意结算后 `Σ sidePots.amount + Σ refunds.amount === 结算前的 Σ totalBet`（退还后各玩家 `totalBet` 已扣减退款额），且弃牌者筹码计入金额但不计入 eligible；每个 `deadMoney` 条目的 `mergedIntoLayer` 必须指向存在的 `sidePots` 下标，且该层 `amount` 已包含这笔死钱（`deadMoney` 不参与守恒等式）。
21. **烧牌**：完整发牌序列与 `deckState` 一致（含 3 个烧牌位），单挑与 6 人桌都能原样重放；全员全下提前发完的分支同样含烧牌。
22. **自动补码**：筹码归零后按买入额补回，在 `poker.session.v2.events` 记一条 `autoRebuy`；补码金额不计入任何手牌的盈亏，也不进入单手守恒断言。
23. **换街清零与快照**：翻前当前注 100、`lastFullRaiseSize` 100，P 跟注 100 → Q 加注到 200（完整加注）→ 断言 `P.actedBeforeLastFullRaise === true`、`P.facedRaiseAmount === 100`（P 上次行动后面对的新增加注额）；进入翻牌后断言所有玩家 `facedRaiseAmount === 0`、`actedBeforeLastFullRaise === false`、`reopenEligible === false`，且 `lastFullRaiseSize === 大盲额`、`raiseAccumulator === 0`。

## 六、AI 设计（要"像人"，不是"很强"）

三档，**共同硬约束：不透视你的底牌**，只用公开信息 + 自己手牌。

| 档位 | 策略 | 诈唬 |
|---|---|---|
| 新手 | 手牌强度阈值：强就跟/加，弱就弃 | 几乎为 0 |
| 普通 | 起手牌表 + 位置调整；翻后看牌力/听牌 | 约 10% 概率 |
| 老手 | 加对手模型（记录你的弃牌率，你弃得多就多下注） | 按对手弃牌率调整，尺度更接近真实 |

- 诈唬 = "自己牌力弱、但对手可能弃牌"时下注，**不是随机乱加**。
- 用 400–800ms 思考延迟，避免瞬间操作暴露强度。
- AI 难度只调三样：**决策表、诈唬频率、对手模型开关**；不改规则引擎。

## 七、教学系统（决定能不能"学会"）

### 7.1 翻前起手牌表（教学近似值，不追求 GTO 精确）

以下是 **6 人桌、无人加注（open）场景**的入池基准，按起手牌组合列出。实现时转成 13×13 网格，同花在上三角、非同花在下三角、对子在对角线。

| 位置 | 牌例（百分比由程序按组合数自动计算） |
|---|---|---|
| UTG | 对子 55+；ATs+、AJo+；KQs、KJs、QJs、JTs、T9s、98s |
| MP | 对子 44+；A9s+、ATo+；KTs+、KTo+；QTs+、QJo+；J9s+、T9s、98s |
| CO | 对子 22+；A2s+、A9o+；K9s+、KTo+；Q9s+、QTo+；J8s+、T8s+、97s+、87s、76s |
| BTN（6-max） | 对子 22+；A2s+、A5o+；K4s+、K8o+；Q6s+、Q9o+；J7s+、J9o+；T7s+、T9o；96s+、86s+、75s+、65s、54s |
| SB（6-max）· 开池（全弃到 SB） | 对子 22+；A2s+、A8o+；K6s+、K9o+；Q7s+、Q9o+；J8s+、J9o；T7s+、T9o；96s+、86s+、75s+、65s |
| SB（6-max）· 面对 BTN open | 3-bet：对子 66+、AQs+、AKo、KQs；跟注：对子 22–55、A2s–A9s、K9s–KJs、QTs、JTs、T9s、98s、87s、76s、65s |
| BTN/SB（heads-up） | 对子 22+；A2s+、A5o+；K5s+、K9o+；Q6s+、Q9o+；J7s+、J9o+；T7s+、T9o；96s+、87s+、76s、65s、54s |
| BB（防守） | 面对不同加注额、有效筹码和多人入池动态计算；不固定百分比 |

- 上述表仅作**无人加注**的入口范围；面对加注、3-bet、多人入池或短筹码时不能直接套用，教学系统先给"基准范围 + 影响因素"，再逐步加入简化调整。
- **「+」的统一语义**：`A2s+` 表示 A 与 2 及以上**所有**点数组成的同花组合（A2s、A3s … AKs），不跳过任何点数；`K9o+` 同理（K9o、KTo、KJo、KQo）。区间写法 `K9s–KJs` 指端点之间连续点数。转 13×13 网格时按此规则展开，不许自行理解成"任意更高张"或"同花色连续"。
- **大盲防守**：按对手加注额、有效筹码和多人入池情况换算底池赔率，不固定承诺某个百分比。

### 7.2 底池赔率

需要的最低胜率 = **跟注额 ÷（跟注前底池 + 跟注额）**。界面变量必须明确为 `potBeforeCall`，不能使用已经包含待跟金额的总池。

界面直接写：`跟注 500，跟注前底池 1500 → 你需要 25% 胜率`。

翻后可显示 `翻牌 outs × 4%`、`转牌 outs × 2%` 的粗略提示，但要标注为近似值；重复 outs、后门听牌、对手范围和隐含赔率不在该公式内。

### 7.3 复盘讲评（每手结束弹出）

逐街给出具体点评，基于当时真实状态重算，模板化但不空泛：

- 翻前：`你在 BTN 用 K9o 平跟。前面已有一人 limper，按「面对 limper 的收紧范围」应弃：K9o 在无人入池的 BTN 可以开池，但多人入池后只剩边缘价值，平跟会让你用弱范围在不利位置打下去。`
- 翻牌：`你击中顶对，底池 1200，你下注 400（1/3 底池）。该尺度给了对手听牌太好赔率，建议 60–70% 底池。`
- 河牌：`你面对 2000 下注弃牌，跟注前底池 4000 → 只需 33% 胜率。这手你实际约 40%，弃得偏紧。`

**每条点评的结构（存进牌谱的 `review` 字段）**：

```
review = { actions: [ {
  actionIndex,            // 对应牌谱里第几个 action
  street,
  verdict,                // 'good' | 'mistake' | 'marginal'
  suggestedAction,        // 建议动作（规则表 + 简化范围评估，见 §14 决策 5）
  assumptions: {          // 必须写全，缺一个就不许输出这条点评
    opponentRange,        // 假设的对手范围
    potOdds,              // 当时的赔率门槛
    effectiveStack        // 当时的有效筹码
  },
  text                    // 展示给玩家的话
} ] }
```

- `suggestedAction` 的来源是「规则表打底 + 简化范围修正」，**不声称 GTO 最优**；界面要把 `assumptions` 一并显示，让玩家知道这条建议建立在什么假设上。示例中的下注尺度和胜率只在对应对手范围、玩家数量、位置和有效筹码假设下成立，不是固定答案。
- 没有 `assumptions` 的点评不允许生成——这是验收第 2 条「点评可追溯」的落地方式。

### 7.4 学习进度

累计手数、按位置/按街道的错误率、每手一句"这手学到了什么"，存进"我的笔记"。

## 八、存储结构（localStorage）

> 文档版本、产品版本和数据 schema 版本独立：当前文档为 v9，数据 schema 仍为 v2；只有字段不兼容时才升级存储 key。

```
poker.save.v2:  { schemaVersion: 2, chips, stats:{ vpip, pfr, won, ev },
                  settings:{ table:'hu'|'6max', aiLevel, blinds, buyIn, autoRebuy: true,
                             messageEnabled: true, avatars: AvatarConfig[] } }
poker.hands.v2: [ { schemaVersion: 2, id, time, seed, deckState, players[], buttonSeat, blinds,
                    board[], actions[], sidePots[], refunds[], result, review,
                    messages: Message[] } ]   // 保留最近 200 手，滚动删除
poker.notes.v2: [ { schemaVersion: 2, id, text, handId } ]
poker.session.v2: { schemaVersion: 2, events: [{ type: 'autoRebuy', amount, time }] }  // 补码不混入单手牌局盈亏
poker.avatar.v1.<uuid>: 'data:image/png;base64,...'   // 头像本体，单独 key，单张 ≤ 8KB
```

- **头像存储硬约束**：本地图片先缩到 **≤ 64×64**、转 base64，**单张 ≤ 8KB**；为每张图片生成随机 UUID 作为 `poker.avatar.v1.<uuid>` key，`AvatarConfig.assetKey` 只存这个 key，禁止使用截短哈希避免碰撞。超限直接拒绝并提示，**不许静默失败**。导出牌谱默认只带 `assetKey`，不带图片本体；换机器导入后找不到 key 就回退内置头像。`poker.avatar.v1` 里的 `v1` 是**头像 key 自己的版本**，与数据 `schemaVersion: 2` 无关；头像结构简单、体积小，不随牌谱迁移。
- `deckState` 是**重放的唯一依据**（发牌时已确定的完整牌序，**含烧牌位**），`seed` 只作可读标识与校验，不单独依赖 PRNG 复现。
- 每个 `action` 保存行动前后快照所需字段（见 §5.1），确保复盘只使用当时状态。
- 提供 JSON 导入/导出。
- `AvatarConfig` 与 `Message` 的字段定义见 §9.1「数据结构」，本节只定存储位置与配额。
- **迁移规则（v1 → v2）**：
  - 启动时先读 `poker.save.v2`；读不到再用 `poker.save.v1` 迁移，写入 v2 key，**旧 key 保留不删**。
  - 缺字段补默认值：`schemaVersion: 2`、`refunds: []`、`sidePots: []`、`review: null`、`deckState: null`、`messages: []`；`settings` 补 `messageEnabled: true`、`avatars: []`；`poker.session.v2` 缺失时新建 `{ schemaVersion: 2, events: [] }`。
  - `deckState` 为 `null` 的旧牌谱：允许查看但标记「不可重放」，重放器遇到它直接提示，**不许猜牌序**。
  - 解析失败或 `schemaVersion` 不认识：不覆盖原数据，把原始字符串转存到 `poker.corrupt.<时间戳>`，游戏以新档启动并向玩家提示。

### 9.1 头像与模拟消息 UI 方案

#### 目标

增强座位识别、行动反馈和牌桌氛围，同时不泄露 AI 底牌信息，不让聊天干扰决策。头像和消息都是牌桌信息层，不能替代赔率、位置和复盘面板。

#### 头像

- 主控玩家显示一个默认扑克风格头像，可从本地选择一张图片替换。
- AI 对手使用固定头像、名称和座位颜色；颜色只用于识别座位，不表示牌力、范围或胜率。
- 每个座位显示：头像、名称、位置、剩余筹码、当前街下注、状态标签。
- 当前行动者头像增加外圈高亮；思考中显示轻微动画；弃牌显示灰度；全下显示明确标签。
- 本地图片的尺寸、格式、存储 key 与配额**一律按 §8 的「头像存储硬约束」执行**（≤ 64×64、≤ 8KB、独立 key）；没有图片或 key 失效时回退到内置 SVG/Unicode 图标。
- P0 不做头像编辑器、联网头像、动态表情和语音头像。

#### 模拟消息

AI 只允许发送短文本消息，消息必须与真实行动绑定。**牌桌上的消息流只有两类**：

1. **行动消息**：下注、跟注、弃牌、全下后偶尔显示，例如「这手打不了」「位置太差」。
2. **情绪消息**：少量牌桌氛围文本，例如「这手有点难办」，不得表达具体牌力。

> **教学消息不属于这里**：它只在玩家点击「为什么」或打开复盘时出现，属于 §7.3 的 `review` 数据，**不进入 `messages[]`、不占牌桌气泡**。混在一起会让实时消息流夹带讲解文本，气泡也被长句撑爆。

消息约束：

- 每次行动最多显示一条，默认 3 秒后淡出；消息频率可在设置中关闭。
- 文本必须来自模板或经过规则校验的生成器，不允许随机输出与牌局无关的长对话。
- AI 不得声称知道玩家底牌、准确猜测玩家手牌，或透露自己的真实底牌和决策依据。
- 消息不能作为 AI 牌力提示；同一类行动使用多个等价模板，避免玩家通过固定措辞反推牌力。
- 复盘里的教学讲解走 `review.actions[].text`，依据写进同一项的 `assumptions`，遵守 §7.3 的「无假设不输出」规则。

#### 界面布局

- 牌桌中央保留公共牌和底池。
- 每个座位按「头像 → 名称/位置 → 筹码/下注 → 状态」垂直排列。
- 当前行动者用外圈高亮；消息气泡显示在头像上方，避免遮挡公共牌和行动按钮。
- 右侧信息面板继续显示底池、要跟金额、底池赔率、有效筹码和位置。
- 底部保留弃牌、过牌/跟注、加注、全下四组主要操作（与 §9 一致）；消息不占用操作区域。
- 复盘弹层显示消息对应的 `actionIndex`，可查看该消息使用的状态快照。
- 最低 1280×720 下，头像、消息和操作按钮不得重叠；消息过长自动截断并提供展开。

#### 数据结构

```text
AvatarConfig = { playerId, source: 'builtin'|'local', assetKey, updatedAt }
Message      = { id, speakerId, actionIndex, type: 'action'|'emotion', text,
                 createdAt, templateKey }
```

牌谱增加 `messages[]`（见 §8）；每条消息必须引用产生它的 `actionIndex`。头像配置进入 `poker.save.v2.settings.avatars`，图片本体存 `poker.avatar.v1.<uuid>`，不把大图片重复写入每一手牌谱。导出牌谱默认只带 `assetKey` 与消息文本。

#### 迭代顺序

1. P0：内置头像、座位状态、行动消息模板、消息开关和牌谱记录。
2. P1：本地头像替换、教学消息（**并入复盘面板**）、「为什么」展开、消息与复盘快照联动。
3. 暂不做：自由聊天、联网消息、语音、复杂表情、根据消息反推牌力的特殊动画。

#### 新增验收条件

> 以下 5 条是 §11 第 4 条的具体展开，也是 §13 第 6 条核验项的依据。

- 头像不遮挡牌面、按钮和赔率信息；1280×720 下可完整操作。
- AI 每次消息都能追溯到一个有效 `actionIndex`，且消息内容与行动类型一致。
- 关闭消息后，规则、AI 决策、牌谱和历史 `messages[]` 完全不变；只停止实时消息生成和显示。
- 导出、导入、重放后，消息顺序和 `actionIndex` 一致；头像缺失时使用默认头像。
- AI 消息文本不包含玩家底牌、AI 底牌，也不做未经假设支持的确定性牌力判断。

## 十一、验收标准（四条硬指标）

1. **规则可验证**：§5.3 的 23 条测试全部通过，且每手牌满足筹码守恒、底池守恒、行动合法性和牌谱重放一致；补码事件不计入单手守恒。
2. **点评可追溯**：每条复盘点评至少引用一个对应 action 的真实快照字段，并注明使用的范围/赔率假设；不能只依据最终输赢下结论。
3. **数据可恢复**：刷新、导出再导入后，牌谱字段和重放结果一致；旧版本数据按迁移规则可读。
4. **消息可追溯且不泄露牌力**：每条 AI 消息都能回溯到有效 `actionIndex`，同一行动有多条等价模板；关闭消息后不再生成或显示新消息，但历史 `messages[]`、规则、AI 决策和牌谱均保持不变。详见 §9.1「新增验收条件」。

## 十二、明确不做 / 风险

- 不做：在线对战、真钱、云同步、职业级 AI、手机端适配。
- 不做自由聊天、联网消息、语音消息、动态表情；AI 消息只能是模板化短文本，且必须绑定到具体 `actionIndex`。
- P0 不做复杂范围求解；先显示精确赔率门槛和可解释的 outs 估算，后续可加入缓存的精确对单一范围胜率。
- 首版桌面优先（最低 1280×720），但要求窗口缩放、文字不遮挡和键盘可操作性。
- 已知偏差：起手牌表是教学近似值，不是 GTO 求解结果；复盘点评是规则化模板，不代表最优解。

## 十三、重点核验项（6 处最易翻车）

1. **边池算法**（§5.2）—— 分档逻辑是否真能覆盖 100/300/500 这种三层全下与三层投入，以及「包含弃牌者的计数、eligible=1 的 `direct`、eligible=0 的死钱合并、奇数余数」四个细节；`direct` 与 `refunds` 是否唯一（同一笔钱不许两条路都记）；`deadMoney` 审计与守恒断言是否自洽。
2. **单挑位置与行动顺序**（§5.2）—— BTN=SB；翻前 BTN/SB 先动，翻后 BB 先动。
3. **底池赔率公式**（§7.2）—— 分母到底含不含自己这次跟注。
4. **AI 是否真的不透视**（§6）—— 有没有从全局状态里偷读玩家底牌。
5. **复盘讲评的数据来源**（§7.3）—— 讲评用的是行动当时的快照，还是结算后的错误状态。
6. **AI 消息会不会泄牌**（§9.1）—— 同一类行动是否用了多个等价模板；措辞、频率、消息类型会不会被玩家反推出牌力；教学消息是否只走复盘而不进实时消息流。

## 十四、已定案的决策（实现时不得自行更改）

> 说明：短盲注规则与短全下累计规则已在 §5.2 定死。本节决策已确定，后续实现不得自行改变。

1. **烧牌：模拟。**每次发翻牌、转牌、河牌前先烧一张；烧牌写入 `deckState` 和牌谱，但不显示给玩家。这样与标准无限注规则一致，也不会影响重放。
2. **筹码输光：自动补码。**玩家输光后按当前桌的固定买入额自动补回，继续练习；每次补码只记一条 session 事件，**不混进任何单手盈亏**；界面显示累计补码次数，避免把补码当成盈利。
3. **P0 盲注：固定 10/20。**先保证规则、教学和测试稳定；P2 再开放自定义盲注，并复用同一套单位化规则。
4. **200 手牌谱：删最旧。**按完成时间保留最近 200 手，行为确定、实现简单；用户需要长期保存时使用 JSON 导出，不按“重要性”自动猜测。
5. **建议动作：规则表 + 简化范围评估。**先由规则表提供基准动作，再根据位置、底池赔率、有效筹码、对手行动和预设对手范围修正；不声称 GTO 最优，点评必须显示采用的假设。P0 可先实现规则表，范围修正作为后续增量，但接口从第一版预留。
